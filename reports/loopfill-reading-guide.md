## 一句话总结

LoopFill 用历史文本检索一次提出多个未来 Token，再用模型浅层循环的预测补洞，把它们放进同一棵草稿树中并行计算；最终仍由完整深度模型决定输出，因此无需额外训练，并保持贪心解码结果或采样分布不变。

这里的 **Fill** 很形象：它要填满的不是显存，而是循环解码流水线里的空档。

## 1. 背景：Looped Transformer 为什么慢？

普通 Transformer 通常是一层接一层地向下计算；Looped Transformer 则把同一个共享模块重复执行 $T$ 次：

```math
H^{(t)}=f(H^{(t-1)},E),\qquad t=1,\ldots,T
```

可以把它理解为：**同一套参数，多思考几轮，再给出答案。**

这种架构提高了参数效率，也允许通过增加循环次数分配更多测试时计算，但自回归生成会更慢：

- 普通模型生成一个 Token，大致走一遍网络；
- 循环模型生成一个 Token，要把共享模块串行运行 $T$ 遍；
- 前一个 Token 没完成，后一个 Token 通常不能开始。

在小 Batch 下，每次循环还可能主要受显存带宽限制，GPU 的计算能力没有得到充分利用。

---

## 2. 已有方法：让不同 Token 在流水线里错位施工

LoopSpec、WaveFront 等方法已经提出了一种自然思路：

1. 当前 Token 还没跑完 $T$ 次循环；
2. 在第 $d \lt T$ 次循环时，先拿浅层隐藏状态预测一个草稿 Token；
3. 假设草稿正确，下一个 Token 提前开始计算；
4. 当前 Token 继续运行到完整深度，最后验证草稿；
5. 猜对就保留后续计算，猜错就回滚。

于是，同一个 Batch 里可能同时有：

- Token A 在做第 8 次循环；
- Token B 在做第 5 次循环；
- Token C 刚开始第 1 次循环。

**但浅层预测一次只能提出一个 Token。**如果每隔 $d$ 步才能提出下一个草稿，加速比会受到 $T/d$ 的限制；一旦猜错，还可能出现流水线气泡。

---

## 3. 核心洞察：两个草稿器正好互补

LoopFill 同时使用两种草稿来源。

| 草稿器 | 如何提出草稿 | 优点 | 短板 |
|---|---|---|---|
| 浅层循环预测 | 用模型第 $d$ 层的隐藏状态预测下一个 Token | 了解当前模型意图，命中率较高 | 一次通常只推进一个 Token |
| 后缀树检索 | 在提示词和历史输出中查找相同后缀，取出它后面曾出现的内容 | 无需模型计算，一次能提出多个 Token | 文本没有重复、输出难预测时容易失效 |

例如，当前前缀是：

```text
I would like
```

后缀树可能找到以前出现过的：

```text
I would like to join Lean Club
```

于是它可以一次性把 `to → join → Lean → Club` 都放进流水线，而不必等浅层模型一个接一个地猜。

更关键的是，两者不是简单地先用一个、再用另一个，而是**共同维护一棵草稿树**：

- 浅层模型提出 `to`；
- 后缀树立刻沿着 `to` 继续检索出 `join → Lean`；
- 某个检索节点到达浅层深度后，模型又能给它补一个新分支；
- 两个来源提出相同 Token 时，共享同一个节点，不重复计算。

这就是论文最核心的结构创新。

## 4. 算法流程：抓住四步即可

### 4.1 向树里添加候选

每个请求有一棵草稿树，根节点代表已经验证的前缀。

- **后缀检索**：使用本地树和全局树。本地树索引当前请求的提示词及已生成内容，全局树索引已完成请求的输出；最长检查 64 个 Token 的后缀。
- **浅层预测**：节点到达指定循环深度后，用 LM head 提出 Top-k 个候选。

### 4.2 给候选打分并剪枝

草稿越多，额外计算越大，因此不能全部保留。

后缀候选的初始边权为：

```math
w(v)=\min\{1,cq(v)\}
```

其中 $q(v)$ 是历史匹配中走到该候选的频率，参数 `c` 用来调节检索草稿相对于模型草稿的重要性。

如果浅层模型给出了预测，就用模型概率更新其子节点权重；不在 Top-k 中的候选被置零。每个节点的最终分数，是从根到该节点的路径权重乘积：

```math
s(v)=s(\operatorname{parent}(v))\,w(v)
```

随后只保留根节点和分数最高的 $N$ 个草稿节点。父节点的分数不低于其子节点，因此保留一个节点时，也会保留它回到根节点的完整路径。

### 4.3 不同深度的节点一起前进

每个 Loop Step，树中活跃节点都前进一层循环，并被打包到同一个 Batch 中。

所以这里并不是减少所有计算，而是：

> **用更多并行、甚至可能最终被丢弃的计算，换取更少的串行循环步数。**

### 4.4 完整深度验证，保留已算内容

根节点完成 $T$ 次循环后，由完整深度分布 $p_T$ 决定真正输出：

- 贪心解码：取完整模型的 argmax；
- 采样解码：从完整模型分布中采样。

如果输出匹配某个子节点，就把该子节点提升为新根，**保留它和后代已经完成的循环计算**；否则才重新开始。

因此，草稿器只决定哪些位置提前开工，不决定最终输出什么。这意味着贪心输出保持一致，采样时保持原自回归分布，而不是接受一种近似输出。

## 5. 图 2 示例：为什么组合方法更快？

论文用 $T=3$ 的例子生成 5 个 Token：

| 方法 | Loop Steps | 相对加速 |
|---|---:|---:|
| 普通自回归 | 15 | $1.0\times$ |
| LoopSpec | 9 | $1.7\times$ |
| SuffixDecoding | 9 | $1.7\times$ |
| LoopFill | 5 | $3.0\times$ |

原因很直观：

- LoopSpec 能提前启动下一个 Token，但一次只猜一个，猜错会产生空档；
- SuffixDecoding 能一次猜多个，却仍需按完整深度逐轮验证；
- LoopFill 既能让多个未来 Token 同时进入流水线，又能在检索失败时用浅层预测补上。

**多 Token 提案负责把流水线拉长，浅层预测负责减少等待和空洞。**

### 5.1 按全局 loop step 逐步读图

图 2（b）中，黄、蓝、绿分别表示 loop 1、2、3；每一列是一个全局 loop step，每一行负责预测一个输出位置。主流程可以进一步拆成：

| 循环步 | 跨深度并行计算 | 双草稿源与统一树调度 | 验证／提交结果 |
|---|---|---|---|
| 1 | 根节点 `like` 到 R1 | 浅层预测提出 `to`；后缀检索提出 `a → coffee`，之后统一评分并剪除低分路径 | 尚无输出 |
| 2 | `like` 到 R2；`to`、`join`、`Lean` 等到 R1 | 以浅层草稿 `to` 为新前缀再次检索，加入 `join → Lean → Hub`；`Lean` 的浅层预测继续补出 `Club` | 尚无输出 |
| 3 | `like` 到 R3；`to`、`join`、`Lean` 到 R2；`Club` 到 R1 | 保留高分路径，`Club` 的浅层预测继续给出换行候选 | 完整深度确认并提交 `to` |
| 4 | `to`、`join`、`Lean` 同时到 R3；`Club` 到 R2 | 三个位置都已完成各自的完整深度验证，剪除 `the`、`Hub` 等竞争分支 | 同一步连续提交 `join`、`Lean`、`Club` |
| 5 | `Club` 到 R3 | 保留匹配子树及缓存状态 | 完整深度确认并提交 `\n` |

第 4 步一次提交三个 Token，不代表只对其中一个位置做了验证，而是三个位置都早已并行完成 loop 3。SuffixDecoding 要等到第 3 步第一轮结束后才启动下一轮，所以要到第 6 步才能提交这三个 Token；LoopFill 则提前把它们填进了流水线。

## 6. 理论分析：理解一个核心公式

论文定义循环归一化平均接受长度：

```math
\gamma=\frac{nT}{K}
```

其中 $n$ 是输出 Token 数，`K` 是实际使用的串行 Loop Steps。它表示：**每 $T$ 个串行循环步，平均能生成多少 Token。**普通自回归解码的 $\gamma=1$。

设：

- $p_s$：后缀草稿命中概率；
- $d$：浅层草稿出现的深度；
- $\alpha$：后缀草稿失败时，浅层草稿仍然命中的条件概率。

则：

```math
\gamma_{\mathrm{LF}}
=
\frac{1}{1-p_s}
\cdot
\frac{T}{\alpha d+(1-\alpha)T}
```

不用死记，拆成三种情况即可：

- 后缀命中：下一个 Token 可以立即开始，延迟为 0；
- 后缀没中、浅层命中：等待 $d$ 步；
- 两者都没中：等待完整的 $T$ 步。

在 Ouro-2.6B 的运行轨迹上，`T=4`、`d=1`、`p_s=0.510`、`α=0.796`，公式预测 $\gamma\approx5.06$，超过只用浅层草稿时 $T/d=4$ 的上限。

不过，这部分理论假设单请求且容量足够；有限节点预算下，检索草稿也可能挤掉本来正确的浅层候选，所以实际系统不会永远满足理想的两者取最优。

## 7. 实验结果：数字漂亮，但要分场景看

论文在 Ouro 和 Huginn 两类循环模型、七个基准上测试，实验使用单张 NVIDIA L20X、BF16。

### 7.1 单请求解码延迟

贪心解码下，相对普通自回归解码的平均加速为：

- **Ouro-2.6B：5.85×**；
- **Huginn-3.5B：5.13×**。

相对最强基线 LoopAhead，分别再提高 **40%** 和 **25%**。

温度升到 1.0 后，平均加速降为：

| 模型 | 贪心解码 | Temperature 1.0 |
|---|---:|---:|
| Ouro-2.6B | $5.85\times$ | $3.50\times$ |
| Huginn-3.5B | $5.13\times$ | $2.60\times$ |

这符合作者的判断：**输出越难预测，历史后缀和浅层预测越容易失配。**

### 7.2 多请求端到端吞吐量

在 SpecBench、Temperature 1.0、并发数 $B=16$ 时：

- Ouro-2.6B 达到 189.56 tokens/s，是 AR 的 $2.81\times$；
- Huginn-3.5B 达到 129.18 tokens/s，是 AR 的 $2.67\times$。

但此时相对次优方法的优势分别只有 **1.6%** 和 **9.9%**。所以，比最强基线高 40% 是单请求贪心延迟结果，不能直接套到所有吞吐场景。

---

## 8. 消融实验：两种草稿都在贡献，但不是越多越好

### 8.1 两种草稿源确实互补

在 SpecBench 上，后缀草稿贡献约 38%—43% 的输出 Token，浅层草稿贡献约 55%—57%。后缀检索在摘要和 RAG 中贡献 50%—61%，但在翻译中只有 16%—18%，说明收益明显依赖文本的可复用性。

### 8.2 草稿预算需要随场景调整

默认配置是 $N=16$、Top-k=2、每次检索最多加入 $Q=4$ 个节点。在 Huginn-3.5B 上，把 $N$ 从 16 提到 64：

- 单请求解码速度提高约 19.5%；
- 16 并发时端到端吞吐量反而下降 43%。

所以，LoopFill 的实际部署重点是：**根据硬件和并发量控制草稿预算，而不是一味扩大草稿树。**

## 9. 讨论补充：后缀预算、Top-N 与节点深度

### 9.1 后缀长度限制并不直接等于模型计算上限

论文中有三个不同的预算概念：

| 概念 | 含义 | 默认值或上限 |
|---|---|---|
| 后缀匹配长度 $p$ | 用当前前缀的多长后缀查询历史续写 | 最长检查 64 个 Token |
| 单次检索预算 $Q$ | 一个匹配后缀最多贡献多少草稿 Token | $Q=4$，并受 $\min(Q,p)$ 限制 |
| 每请求节点预算 $N$ | 每轮最多保留多少非根节点参与计算 | $N=16$，根节点额外保留 |

对于匹配成功的后缀，单次加入量受下式限制：

```math
\min(Q,p)
```

所以，64 是“向后查看多少上下文”，不是“向前生成多少草稿”；`Q=4` 只限制单次检索，多次浅层预测和再次检索仍能延长草稿链。LoopFill 会检查不同长度和两棵后缀树，但只选择分数总和最大的一个候选子树合并，而不是合并全部匹配结果。

真正直接限制目标模型计算量的是 $N$。若有 $B$ 个请求，每个请求每步最多使用 $N+1$ 个节点位置，则 $S$ 个全局 loop step 的最坏循环节点计算量上界为：

```math
C_{\mathrm{loop}}\leq S\cdot B(N+1)
```

实际量通常低于该上界，因为候选会提前剪枝，且并非所有节点都运行到完整深度。后缀长度主要影响检索覆盖与 CPU 查询成本，`Q` 影响候选丰富程度，`N` 最直接地决定每轮 batch 上界。全局后缀树的文本索引大小不受 $N$ 限制，需要单独考虑其长期内存和查询成本。

### 9.2 Top-N 如何筛选，以及 like、to、the 为什么不同

后缀检索创建边时使用 $w(v)=\min(1,cq(v))$ 作为初始权重；节点到达浅层深度后，top-k 子节点改用模型概率，不在 top-k 中的已有候选置零。每个节点的最终分数是从根到该节点的路径权重乘积。

树更新后，LoopFill 将所有非根节点统一按路径分数降序排列，保留前 $N$ 个。父节点始终排在子节点之前，因此保留深层节点时，也会保留它回到根的完整祖先链。被 Top-N 筛除只是失去后续加速计算，完整深度模型仍能保证最终输出正确。

图 2（b）中的候选可简化为：

```text
like
├── a → coffee                 后缀检索链，之后剪枝
└── to                         浅层草稿
    └── join                   后缀与浅层共同支持，合并计算
        ├── the                浅层草稿，错误分支
        └── Lean               后缀草稿
            ├── Hub            后缀竞争分支
            └── Club           浅层草稿
                └── \n         浅层草稿
```

因此，`a` 和 `coffee` 不是 `like` 的两个独立直接子节点，而是后缀树一次提供的连续路径。对于 `to`，后缀树和浅层模型都提出 `join`，同父同 Token 的候选会合并，所以只保留一个节点并计算一次。

图中第 3 步没有显示 `the` 的后代，不能据此推断算法禁止它执行浅层 readout。按一般规则，只有被保留且到达起草深度的节点才会继续扩展，而示意图只展示与主流程相关的候选。能够确定的是：`the` 在第 4 步完整深度验证 `join → Lean` 后被拒绝；论文正文没有进一步说明它是否曾产生过未画出的临时子节点。

### 9.3 d 是节点自身深度，不是全局时间列

浅层起草深度 $d$ 表示**某个节点自己已经完成的循环次数**。到达 $d$ 后，节点会提前调用 LM head 产生草稿；只有到达完整深度 $T$ 后，才能最终验证。

例如 $T=4,d=1$ 时：

```text
Step 1：节点到 loop 1，产生浅层草稿，继续向深层推进
Step 2：节点到 loop 2，继续完善隐藏状态
Step 3：节点到 loop 3，继续完善隐藏状态
Step 4：节点到 loop 4，执行完整深度验证
```

全局 step 是图上的时间列，`d` 是节点自己的循环进度。老节点可能正在完成 loop 3，新加入的节点则可能才刚开始 loop 1。较小的 $d$ 能更早产生候选，但通常可靠性较低、错误分支更多；较大的 $d$ 草稿更可靠，却会减少流水线提前量。

## 10. 阅读评价与证据边界

这篇论文最有价值的地方，不只是又做了一个推测解码方法，而是把两种看似独立的加速维度接上了：

- **循环深度方向**：浅层预测减少 Token 之间的启动间隔；
- **序列方向**：后缀检索让多个未来 Token 同时进入流水线。

同时，它保留了两个实用性质：**免训练、完整深度验证**。需要注意，免训练不等于零系统成本——后缀树维护、草稿调度、额外节点计算和分支复用都需要推理引擎配合。

阅读证据边界时还要记住：

1. 当前实验集中在 1.4B—3.5B 的两类模型和单一 GPU 环境；
2. 高随机性采样、高并发以及低可预测文本上的收益会收缩；
3. 大草稿预算可能改善单请求延迟，却损害多请求吞吐量；
4. 论文结论能否迁移到其他循环架构和硬件，需要重新测量，而不能直接外推。
